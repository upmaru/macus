# Per-user packaging

One Macus installation supplies the `macus` executable and the paired bundled-ERTS Macus server release. From a checkout with Swift installed:

```sh
Packaging/install-local.sh --prefix /absolute/path
```

The default prefix is `~/.local`. Use an absolute isolated prefix for tests and acceptance; do not point it at a runtime state directory. The installer builds, stages, ad-hoc signs and verifies the `macus` executable and the paired bundled-ERTS Macus server release, then installs them at `prefix/bin/macus` and `prefix/libexec/macus`. It downloads the opsmaru_incus cassette for the locked version from its upmaru/opsmaru-incus GitHub Release, or takes the one given with `--cassette`, and refuses it unless its `.sha256` and `gh attestation verify` accept it; this needs the GitHub CLI, signed in ([development](../docs/development.md#macus-command)). The executable carries `com.apple.security.virtualization` for its `serve` mode. Client commands still require explicit runtime operations and never start the daemon implicitly. Existing runtime data is not created or modified.

This source install requires Swift and Elixir/Erlang and produces development ad-hoc signatures. It does not install Homebrew, the Incus CLI or a launch agent. Unsafe destinations, a release whose identity differs from the executable's and a missing pinned dependency are refused before anything is installed. `macus start` refuses an installation without a paired release with `invalid_configuration`, before downloading or activating anything. `macus client setup` is the explicit later step for the standard Incus CLI. No formula or checksum is published until real release artifacts exist.

Build and ad-hoc sign a development binary using docs/development.md. For a persistent local installation, copy it to a user-owned absolute path, replace `@BINARY_PATH@` and `@STATE_PATH@` in `Packaging/launchd/com.upmaru.macus.plist.in` with absolute paths (XML-escape values), and save the completed plist under `~/Library/LaunchAgents/com.upmaru.macus.plist`. Validate with `plutil -lint`, then bootstrap using `launchctl bootstrap gui/$(id -u) <absolute-plist-path>`. Unload using `launchctl bootout gui/$(id -u)/com.upmaru.macus`. This template starts the Swift control socket at login and does not boot Linux until a runtime command asks for it. It covers only the Swift job: `macus runtime`, `doctor` and `client setup` also need the Macus server job, `com.upmaru.macus.server`, which has no template here because `macus start` writes it ([service pair](../docs/cli.md#service-pair)). Project checks do not install an agent or modify launchd. `macus start` registers both default jobs, or session-only `com.upmaru.macus.<state-hash>` and `com.upmaru.macus.server.<state-hash>` jobs under an explicit nondefault state. Isolated start does not replace the plists in `~/Library/LaunchAgents`. No Opsmaru or other third job is created.

To update a source installation that `macus start` has registered, follow the same stop and unload sequence as a package change ([upgrade, rollback and removal](homebrew/README.md#upgrade-rollback-and-removal)): `runtime stop`, `launchctl bootout` the server job and then the Swift job, remove the server job's plist, rerun `Packaging/install-local.sh` into the same prefix, then `macus start`. The installer never touches launchd or the state, so disks and credentials stay in place.

The service starts its API on login and boots Linux only when requested through the runtime API. Unloading preserves disk state. `ExitTimeOut` exceeds the default graceful shutdown timeout; explicit callers can choose longer deadlines. Development binaries are not signed/notarized distribution artifacts.

When replacing an existing launch agent, explicitly unload `com.kritama.tama-incus-mac` and `com.kritama.macus`, and remove those plists from LaunchAgents, before installing `com.upmaru.macus`. Set its binary path to the installed `macus` and keep its existing state path. Do not activate both a legacy agent and `com.upmaru.macus` against one directory. `macus start` detects those legacy registrations and stops rather than unloading them or starting a second daemon. The installer leaves legacy executables in place and does not perform this service transition. Service logs use the `com.upmaru.macus` subsystem.
